- 取り組んだレベル：実装

- やったこと（変更したファイル・設定・処理、または設計した取得方法）：

`app/retrieval.py` に `search_with_neighbors()` を実装し、
  ベクトル検索で取得した各ページについて、同じ資料の前後1ページを
  追加取得する処理を導入。

  また、`app/tools.py` の `search_materials()` を変更し、
  通常の検索結果に隣接ページを追加してモデルへ渡すようにした。

  ページIDによる重複排除を行い、追加したページには
  `retrieval_type` と `neighbor_of` を付与して、
  通常の検索結果と区別できるようにした。


- 比較した質問と、固定した条件（モデル・対象資料など）：

質問：
  「第2回の説明では、LoRAは何を固定し何を学習しますか？
  QLoRAは何を加えますか？」

  モデル：gemini-3.5-flash-lite
  対象資料：第1～3回の講義資料

  変更前後で同じ質問を使用し、通常のRAGと、
  前後ページを追加するRAGの回答を比較。

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

 | 項目 | 変更前 | 変更後 |
  |---|---:|---:|
  | 回答時間 | 2.94秒 | 3.20秒 |
  | 入力トークン | 3,905 | 6,672 |
  | 出力トークン | 176 | 202 |
  | 推定API費用 | $0.001612 | $0.002507 |
  | モデル応答回数 | 2回 | 2回 |

  変更前後ともに、元の重みを固定して行列A・Bを学習するLoRAと、
  元の重みを4bit量子化するQLoRAについて正しく回答した。
  参照ページも第2回資料のp.51・52で一致しており、
  この質問では回答品質の明確な改善は確認できなかった。

  一方、検索結果は変更前の5ページから変更後は11ページとなり、
  隣接する6ページが重複なく追加された。


- 改善した例と、残る失敗・制約：

 　LoRA・QLoRAの学習方法と、チャットボットにおけるFTとRAGの使い分けを同時に質問。

  この質問に対する通常検索では、第2回資料のp.53は取得されたが、
  LoRA・QLoRAの仕組みを説明するp.52は取得されなかった。
  拡張検索では、p.53の前ページとしてp.52が追加され、
  両方のページを参照した回答が生成された。
  このことから、前後ページの追加によって、
  検索結果だけでは不足する関連情報を補完できることを確認。

  また、最初の比較では入力トークン数が約71%増加し、
  推定API費用も約56%増加。
  関係の薄い隣接ページも追加されるため、
  必ずしも回答品質の向上につながるとは限らない。


- 気づき・疑問：
    RAGでは検索結果の上位ページだけでなく、
  その前後の文脈も重要になる場合がある。
  単純に前後1ページを追加すると、必要性の低い情報までモデルに渡され、コストが増加。

  隣接ページを無条件に追加するのではなく、
  質問との関連度に応じて追加するページを選択することで、
  回答品質とコストのバランスを改善できるのではないか。
